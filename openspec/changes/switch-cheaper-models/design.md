## Context

索引链路上有四处付费调用，代价结构极不对称：

```
clone → parse → summarize ──────► embed ──────► graph ──► report
                    │                │                       │
              SUMMARY_MODEL    EMBEDDING_MODEL         SUMMARY_MODEL
              调用次数最多        token 量最大          （同一个模型）

              在线问答另走 CHAT_MODEL + RERANK_MODEL，本次四个槽位全部切换
```

2026-09-04 onyx 那次索引的实测分布（worker 日志）：

| 类型 | 成功调用 | 说明 |
|---|---|---|
| `chat/completions` | 5938 | 其中约 2726 次是 OOM 重跑白烧的 |
| `embeddings` | 669 | 余额在此耗尽，真实用量远未跑完 |
| `embeddings` 402 | 12011 | 余额耗尽后的重试风暴，不计费但空转九分钟 |

三个约束决定了这次改动的形状：

1. **换嵌入模型是数据迁移，不是改配置**。`graph/client.py:50` 在启动时校验向量索引维度，不符直接拒绝启动；`pipeline.py:431` 检测到 model/dim 漂移会强制全量重嵌入。两处防护都已存在且正确，迁移必须顺着它们走。
2. **窗口期**。Neo4j 当前只有 ColaMD 一个项目、339 节点。迁移代价现在约等于零，随项目增长而线性上升。
3. **候选模型尚未实测**。用户已定案四个百炼模型（`qwen3.8-flash` ×2、`qwen3.7-text-embedding-flash`、`qwen3.7-text-rerank`），但可用性、嵌入实际返回维度、限速档位都还是文档推断，探针要用用户的 key 逐一实测。

## Goals / Non-Goals

**Goals:**

- 把索引一次大仓库的模型开销降到当前的一个数量级以下，且有账单或指标佐证，不靠估算。
- 在迁移代价最低的窗口内完成嵌入模型切换，路径可回滚。
- 用既有的检索评测 harness 给出「质量没退化」的客观依据，而不是主观感觉。
- 让 `indexing-pipeline` 规格重新反映现实（供应商无关），并把「换嵌入模型 = 受控迁移」这条隐含约定显式化。

**Non-Goals:**

- 不做运行时可插拔的多供应商配置层（UI 改 key、自动降级链）。那是独立议题，本次只换默认值。
- 不改重试、并发、超时策略。402 重试风暴与 OOM 重跑是真问题，但属于「索引成本与失败韧性」，另立。
- 不追求「最便宜」。质量退化到影响检索可用性的省钱是负收益。

## Decisions

### D1：先摘要后嵌入，两步分开验证

摘要模型切换是纯配置、零数据影响、随时可回退；嵌入模型切换是不可逆的数据迁移。把它们合成一步做，一旦检索质量下降就无法判断是哪个变量造成的。

顺序固定为：建立质量基线 → 换摘要模型 → 验证 → 换嵌入模型 → 再验证。每步之间留一次可回退的静止点。

**替代方案**：一次性全换，省一轮验证时间。否决，因为归因能力比那点时间值钱——这次 OOM 重跑的教训正是「多个变量叠在一起时，事后无法拆解」。

### D2：候选模型的可用性与维度必须实测，不接受文档推断

定价页对嵌入模型的信息前后不一致（两次抓取，一次说 `BAAI/bge-m3` 免费、`Pro/` 版 ¥0.07，一次说查不到），而余额为 0 时连免费模型都被拒，无法用「调通了」来反证免费。

因此拿到 key（本地 `~/.peco-dashscope.key`）后的第一个动作是探针脚本：对每个候选模型发一次最小请求，记录 HTTP 状态、**实际返回的向量维度**、以及调用前后的账户余额差。维度尤其重要——`EMBEDDING_DIM` 与模型实际输出不符会让向量索引建错，而这个错误要到检索质量明显异常时才会暴露。

**实施后记（2026-09-07）**：探针按此做了，维度确实抓准了，却漏了另一种延迟失效——探针体只有几十字节，而 `qwen3.7-text-embedding-flash` 的服务端对约一半**真实尺寸**的输入体挂起不响应（tcpdump 证明请求被完整 ACK、零重传、15 秒无回包；境内外两地一致）。探针必须包含与生产同尺寸的请求体（批 10 × 3000 字符）。已改选 `qwen3.7-text-embedding`。

**替代方案**：直接按文档标称的 1024 维配置。否决，属于「延迟一步的失效」——建索引时不报错，写入时不报错，只在检索结果变差时才显形，而那时已经索引完所有项目。

### D3：迁移路径顺着既有防护走，不绕过它们

```
1. 记录基线      eval harness 跑一次，存指标 + 配置指纹
2. 停 worker     避免迁移中途有任务写入旧维度向量
3. DROP 三个向量索引
4. 改 .env       EMBEDDING_MODEL / EMBEDDING_DIM 同时改
5. 起 backend    维度校验通过 = 索引已按新维度重建
6. 重索引        pipeline 检测到模型漂移，自动走全量路径
7. eval 对比     与第 1 步的指标比对
```

第 2 步与第 5 步的顺序不能调换：backend 启动时才会建向量索引，而 worker 若在索引不存在时接到任务会写入失败。

**为什么不加「双写过渡」**：新旧向量维度不同，无法共存于同一索引，双写需要两套索引加一层路由，复杂度远超收益——当前只有一个小项目要重索引。

### D4：质量验收用既有 harness，指标先于感觉

`services/rag/scripts/eval_retrieval.py` 配 `tests/eval/golden_set.json` 已经能在真实模型下跑出可比指标，规格里「真实模型评测档」这条需求就是为这类变更准备的。

判据定死在动手之前：**新模型的检索指标不得低于基线的 90%**。低于就回滚嵌入模型，保留摘要模型的切换（两者独立）。不设「差不多就行」的模糊标准——省钱的诱惑会让人事后放宽判据。

**已知局限**：golden set 基于 fixture 仓 mini_repo，规模远小于真实项目，指标持平不等于大仓库上也持平。这是接受的残余风险，缓解手段是 ColaMD 重索引后人工抽查几条真实查询。

### D5：摘要与问答统一用 `qwen3.8-flash`，限速仍要探

用户定案两个 LLM 槽位都用 `qwen3.8-flash`（¥1 / ¥3）。摘要任务的输入是文件头 600 字符加符号清单 1500 字符，输出 `max_tokens=500` 的一句话概括，代码注释本身写着「摘要略糙可接受，摘错则会误导」，flash 档够用；问答用同一个模型省去两套限速与账单口径。

**限速是真风险**：摘要并发 4、单个大仓库几千次调用，硅基流动那次已撞出 454 次 429。百炼对新账号的 RPM/TPM 档位未知，探针阶段要做一次并发 4 连发 20 次的压测；触发限流优先在控制台申请提额，而不是调低并发——降并发会让大仓库索引时间线性变长，反而增加 OOM 窗口。

### D7：重排通过 provider 开关适配，不改现有路径

`qwen3.7-text-rerank` 的接口与现有 Cohere 风格客户端有三处不同：完整端点 URL 带 WorkspaceId（`https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api/v1/services/rerank/text-rerank/text-rerank`）、请求体嵌套在 `input` / `parameters` 下、响应在 `output.results`。

做法：`rerank_provider` 配置项，默认 `cohere`（一行不改，硅基流动路径与全部既有测试原样），`dashscope` 时 URL 直接取 `rerank_base_url` 不再拼 `/rerank`、体改嵌套、响应先剥 `output` 再交给现有 `parse_ranking`。失败哲学不变：任何异常都返回 None，问答保持原顺序。

**替代方案**：改选 `qwen3-rerank`（百炼的 OpenAI 兼容路径，扁平体），只差路径 `/reranks` 一个字母。否决——同样要改代码，而且那条路径也要 WorkspaceId 域名，省不下什么；用户已定案 `qwen3.7-text-rerank`。

**为什么不先留空**：留空即退回 RRF，零风险，但用户明确要重排。适配本身十几行且有 mock 测试兜底，风险可控；真正的未知是 WorkspaceId 与限速，都在探针阶段解决。

### D6：分时定价属于运维习惯，不写进代码

`deepseek-ai/DeepSeek-V4-Flash` 夜间时段单价减半。onyx 那次跑在北京时间 10:43–13:24，全价。这条省钱路径不需要任何代码改动，只需要「大仓库索引排夜里跑」的习惯，记进 server-notes 即可。

**替代方案**：做一个「低价时段队列」，任务自动延迟到折扣窗口执行。否决，收益不确定（换了摘要模型后单价差已经不大）而复杂度实在（延迟执行要处理用户预期、任务超时、队列积压）。

## Risks / Trade-offs

**[`qwen3.7-text-embedding-flash` 是通用文本嵌入的轻量档，不是代码专用]** → 代码检索质量可能不如 Qwen3-Embedding-8B。缓解：D4 的指标门槛负责拦截；重排层换成 `qwen3.7-text-rerank` 后仍在，对首轮召回的瑕疵有二次纠正；且回滚只需重索引一个小项目。

**[重排适配是新代码，接错了会静默退回 RRF]** → 失败哲学是任何异常返回 None，所以接错的表现是「问答正常但排序没变」，不会报错。缓解：6.1 开启后必须查日志无 `rerank 调用失败`，并用 eval 对比开关前后的指标。

**[候选模型可能不可用、限速过严或价格与文档不符]** → 探针一跑就知道，此时尚未做任何破坏性操作。这也是把探针放在第一步的原因。

**[维度从 4096 降到 1024，信息量客观减少]** → 这是本次最实质的取舍。收益是 API 费用与 Neo4j 内存双降，代价是向量表达力下降。承认它是取舍而非纯赚，用 D4 的指标决定是否接受。

**[迁移期间检索不可用]** → DROP 索引到重索引完成之间，`/rag` 的问答会检索不到内容。当前只有一个项目、几分钟窗口，影响可接受；执行时机仍应避开使用时段。

**[摘要模型换了，历史摘要仍是旧模型产出]** → 新旧摘要风格不一致，但都存在 Neo4j 里正常可用，不影响检索。全量重索引时会自然统一。不为此单独重跑。

## Migration Plan

见 tasks.md 的分组顺序：前置验证（探针，无破坏）→ 基线（eval 跑一次）→ 摘要与问答模型（可回退）→ 重排适配代码合入但不开启 → 嵌入模型迁移（不可逆，含 DROP 索引）→ 开启重排与验收 → 收口。

**回滚**：

- 摘要/问答模型：改回 `.env` 的 `SUMMARY_MODEL` / `CHAT_MODEL` 与 `CHAT_BASE_URL` / `CHAT_API_KEY`，重建 backend/worker，即时生效，无数据影响。
- 重排：`RERANK_*` 三项清空即关闭，退回 RRF，重建 backend。
- 嵌入模型：改回 `EMBEDDING_MODEL` 与 `EMBEDDING_DIM`，再次 DROP 三个向量索引，重索引全部项目。代价与正向迁移相同——这正是要趁项目少时做的理由。

## Open Questions

- **百炼 WorkspaceId**：重排端点域名需要它，用户要在百炼控制台查。拿到前重排先留空（退回 RRF），不阻塞其他三个槽位的切换。
- **限速档位**：百炼对该账号的 RPM/TPM 未知，探针压测后决定是否申请提额。
- **usage 字段未落日志**：SDK 返回的 token 用量目前没有记录，导致成本只能靠账单反推、无法按项目或阶段归因。修它很小，但属于可观测性而非本次范围，待定是否并入。
