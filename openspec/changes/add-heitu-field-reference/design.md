## Context

`/front` 是**作品集橱窗**，不是文档站。这个定位是本设计的地基：heitu 自己已有 dumi 文档站
（`dumi dev` / `docs:build` / `gh-pages -d dist`），API 完备性是那边的职责。橱窗承诺的是另一件事
——**你在页面上看到的东西，我都解释得清**。

当前四个 tab 的 TSDoc 覆盖率极不均匀（统计自 `node_modules/heitu/dist`，排除 esm 副本）：

| 模块 | 成员行 | TSDoc | 覆盖率 |
|---|---|---|---|
| components（FormRender） | 37 | 36 | 97% |
| charts | 76 | 58 | 76% |
| hooks | 109 | 37 | 33% |
| canvas | 274 | 17 | 6% |

canvas 的 274 行中大半是 `calcWholeRingD()`、`deg2rad()` 等 class 上的内部方法与缓存属性，本就不该进橱窗。
**判据是声明位置而非名字**：同名的 `path2D` 在 `Circle` 上是 draw 写回的内部缓存（class 属性，不展示），
在 `ICustom` 上却是必填的构造参数（interface 字段，必须展示）。按名字拉黑会误删后者。
真正需要人工补写说明的量远小于 258。

既有的 `app/front/demos/hooks-reference.ts`（165 行手抄）是本 change 要解决的问题的样本，
而非可复制的范式：其文件头自称「与当前安装版本一致」，但无任何机制守护该断言，而 heitu 已升级过一次。

## Goals / Non-Goals

**Goals:**

- 四个 tab 均有字段说明，且页面上不存在空白说明
- 内容漂移时**能被发现**——heitu 改名、删字段、加字段，生成流程必须失败或提示
- 人工债务随上游完善而**自动缩小**，不永久携带
- 保住 `hooks-reference.ts` 中人工润色过的中文，只把会腐烂的部分交给脚本

**Non-Goals:**

- 不做 API 完备的文档站——那是 heitu dumi 站的职责，重复建设只会产生两个互相矛盾的正本
- 不修改 heitu 源码补 TSDoc（方案①）——已评估并否决，见下
- 不引入 CI——本 change 不承担为仓库开第一个 workflow 的责任
- 不提供「默认值」列
- 不触碰 `/front` 之外的任何路由、鉴权或数据层

## Decisions

### D1：peco 侧覆盖层（方案②），而非回源头补 TSDoc（①）或只展示有注释的字段（③）

①（在 `../heitu-platform` 补 TSDoc 后发版）收益最大——IDE 悬浮提示、dumi 站、包内四份
`.claude/skills/*.md` 全部受益，且真相源唯一。否决原因是节奏：它要求跨仓改动 + 发版 + 升级，
而执行会话都在 peco-platform，会把一个展示页的改动阻塞在另一个仓库的发布周期上。

③（无注释即不展示）零成本，但 canvas 覆盖率仅 6%，该 tab 会整体空掉，等于没做。

②的固有弱点是「说明与真相源分离 → 会漂移」。本设计通过 D2 将其转化为**可发现的漂移**：
覆盖层的键即 `接口名.字段名`，它同时充当策展清单与漂移探针。弱点未被消除，但从静默变成了会响。

选择②不排斥①。若日后在 heitu 侧补齐 TSDoc，未被覆盖的字段会自动采用上游文本；已被覆盖的
则保留人写版并提示两者并存（优先级见 D11）——两者是互补关系，不是竞争关系。

### D2：覆盖层的键即守卫

覆盖层不是单纯的补丁表。它以 `接口名.字段名` 为键，因而脚本可以在三个方向做一致性检查：
点名的接口是否还在、点名的字段是否还在、展示的字段是否两处皆无说明。第三项尤为关键——
它使 heitu **新增**的字段也无法悄悄溜过去。

这正是 `hooks-reference.ts` 缺失的东西：手抄表与 `.d.ts` 之间没有任何可机械验证的关联。

### D3：纯 AST 解析，不启用 TypeChecker

用 `ts.createSourceFile` 遍历语法树，而非 `ts.createProgram` + TypeChecker。

TypeChecker 能真正展开 `Omit<IChartConfig,'container'> & { style, className }` 这类类型运算，
得到最终属性列表。但既然 D5 已决定不展开继承，展开能力反而是负担：它会把 antd 的 `FormProps`
一并解析进来，再需要一层过滤把它们剔除回去，同时引入对 antd 类型解析成功与否的隐性依赖。

纯 AST 按接口名定点提取，行为可预测，失败模式简单（找不到就报错）。`typescript` 已是
devDependency，脚本作为 `.mjs` 直接 `import ts from "typescript"` 即可，与 `scripts/migrate.mjs`
的形态一致，不新增依赖。

**已知代价（实施中确认）**：`IChartProps` 那一族是 `Omit<IChartConfig,'container'> & {...}` 的
type alias intersection，纯 AST 取不到其成员。因此 charts 的清单点的是 `*Config` 接口而非
`*Props`，Props 侧独有的 `style` / `className` 无法进入 fields，只能在表脚注明。这是 D3 换取
可预测性所付的确定代价，接受。

### D4：策展范围 = demo 里实际出现过的字段

橱窗不承诺 API 完备，因此展示边界需要一条不靠临场判断的规则。「页面演示了什么就解释什么」
使 canvas 的覆盖量从 258 条压到约 35 条，且该边界自洽——观众不会看到未被演示的字段，
也就不会产生「这个参数怎么没解释」的困惑。

### D5：继承一律不展开

`IFormRenderProps extends FormProps` 展开会带入 antd 数十个字段；四种图表均
`extends IChartConfig`，展开会使十余行公共配置重复四遍。改为：子类型只列自有字段 + 一行继承说明，
`IChartConfig` 的公共字段单列一张「图表通用配置」表，全站出现一次。

这同时映射了 heitu 自身的类型层次，读者理解成本更低。

### D6：生成物入库，而非构建期生成

沿用 `app/fonts.css` 的既有约定（脚本生成、不要手改、产物进版本库）。

除保持一致外还有一项额外收益：heitu 升级时，字段变化会直接出现在 PR 的 diff 里——
「新增 `smooth`」「`point` 类型变了」一眼可见。若改为构建期生成，这些变化将不可见。

代价是需要有人记得重跑。见风险 R1。

### D7：`hooks-reference.ts` 拆解而非删除或保留

该文件的 `signature` 字段会随版本腐烂，`desc` 字段是人工润色过的中文、质量优于裸 TSDoc。
因此拆成两半：`signature` 改由脚本从 `.d.ts` 提取，`desc` 迁入覆盖层。

保留原文件会导致四个 tab 中三个自动、一个手抄，一年后无人分得清哪个是权威；
整体替换为提取版则会丢失已有的润色，页面质量不升反降。

**实施中的修正（前提只有一半成立）**：迁移时发现 19 个 hook 里有 6 个源里已有 TSDoc，
与人工 desc 正面冲突——而逐条比对的结果是**有输有赢**，并非 D7 原先假设的「人工一律更优」。
`usePrevious` 的 TSDoc 写明了「首次渲染返回 undefined」而人工版漏了，`useWindowSize` 的
TSDoc 给出了 SSR 下的具体返回值。

因此「一句不丢」被修正为**逐条取优**，判据是：**面向使用者的说明优于面向实现者的说明**。
橱窗读者要知道的是「这个 hook 干什么、何时用」，不是它内部如何遵守 Rules of Hooks。
按此判据 4 条保留人工版、2 条改用 TSDoc，被取代的覆盖条目从 `OVERRIDES` 中删除。

当时不选「hooks 这组改为 OVERRIDES 优先」，理由是「为局部收益牺牲全站统一的优先级规则」。
**该理由随后被 D11 推翻**：把优先级在全站统一反转为「人写优先」后，统一性非但未被破坏，
反而消除了原有的不一致。此处保留原判与推翻记录，以免后来者误以为是反复。
也不选「维持现状让好文本被吃掉」——那会让提示长期常亮，而常亮的信号等于失效。

**衍生约束**：覆盖层的说明 MUST 自包含。迁移过来的文本里有两条以「同上」开头，依赖表格
相邻行才读得懂；橱窗的表可能重排或筛选，任何依赖相邻行的表述都是隐患，须改写为独立成句。

### D8：数据源限定为 `node_modules/heitu`

不引用 `../heitu-platform`。`Dockerfile` 只 `COPY . .`，容器构建环境中不存在隔壁仓库；
且 npm 包版本与 `package.json` 锁定一致，展示内容天然对应实际安装的版本。

### D9：脚本以 transpile + `data:` URL 读取 `curation.ts`

Node 20（本机 v20.19.6，Dockerfile 基础镜像亦为 `node:20-alpine`）不支持
`--experimental-strip-types`，`.mjs` 脚本无法直接 import `.ts`。三个备选：

- **curation 写成 `.mjs`**：脚本可直接 import，但 `tsconfig.json` 的 `include` 只含
  `**/*.ts` / `**/*.tsx` / `**/*.mts`，该文件将完全脱离类型检查——而它正是人要手写
  约 45 条覆盖的地方，最需要类型兜底。把 `**/*.mjs` 加进 `include` 则会连带把
  `eslint.config.mjs`、`postcss.config.mjs`、`scripts/migrate.mjs` 一并纳入检查，影响面过大
- **脚本用 AST 解析 `curation.ts` 的字面量**：可行但啰嗦，且每次结构调整都要改解析逻辑
- **采用：`ts.transpileModule` 转译后经 `data:` URL 动态 import**，约 5 行，`typescript` 已是依赖

代价是 `curation.ts` 中**只能出现 type-only import**：转译产物须自包含，值导入会使相对路径
解析失败。`isolatedModules: true` 保证 `import type` 被完整擦除。该约束已写入 `curation.ts` 文件头。

已实测验证：转译产物无 import 残留，动态 import 正确返回 `CURATION` 与 `OVERRIDES`。

连带调整：契约从两文件拆为三文件——`types.ts`（契约）/ `curation.ts`（内容，人写）/
`generated.ts`（数据，脚本生成）。契约独立后脚本只生成数据，不必在脚本里 hardcode 类型定义的
模板字符串，改产物结构时无需动脚本。

### D10：hooks 用独立的函数形态，重名消歧暂不进契约

实现中撞上两件事，一并在此定夺。

**其一，hooks 装不进 `MemberGroup`。** 19 个 hook 是各自独立的 `declare function`，散在
`hooks/useXxx/index.d.ts`，没有共同的宿主接口——套用 `interfaceName + fields` 会要求虚构一个
不存在的接口名。故 `CurationGroup` 改为联合类型：`MemberGroup`（默认）与 `FunctionGroup`
（`kind: "functions"` + `from` 指定搜索范围）。

做成联合类型而非给 `MemberGroup` 加可选字段，是要让 tsc 强制两种形态被分别处理。但注意这层
保护只覆盖 `curation.ts`（`.ts`，在 tsconfig 内）——生成脚本是 `.mjs`，不受类型检查，因此脚本
MUST 显式分派 `kind` 并对无法识别的形态报错退出，不得静默跳过。

产物侧两者仍统一为 `FieldTable`：members 的行是「字段名 / 类型 / 说明」，functions 的行是
「函数名 / 签名 / 说明」，页面无需分支。

**其二，dist 中存在同名声明。** 排除 esm 副本后实际只有三处：`ICoord`、`Options`、`Setter`。
其中 `Options` 在 `usePolling` 与 `useWebSocket` 各一份且成员完全不同，静默取第一个会产出
张冠李戴的字段表——比报错有害得多。脚本现有处理是正确的：同名且成员不同即非零退出并列出
全部候选路径；成员一致（同一声明被两处 re-export）才取任一。

**不为此在契约里加 `sourceFile` 消歧字段**：选定函数形态后 hooks 不再点名 `Options`，唯一会
触发的场景消失了；剩余两处重名尚未被任何清单点到。脚本已能「响」而非静默出错，等真撞上再加
不迟——现在加是为未发生的问题增加契约复杂度。

### D11：优先级反转——人写优先于机器提取，签名同样可覆盖

实施第 7 组时前端指出：D7 把「机器的」与「人的」按**字段**切（signature 归机器、desc 归人），
但真正的分界不在字段上，而在「哪一份更适合橱窗」。这个判断是对的，且与后端在 7.1 报出的
6 条冲突同源——是同一个问题的两面。

证据：脚本提取的 `useHtAxios` 签名 814 字符（手写版 78），全体中位数 108 对 90。在三列表格中
814 字符要占七八行、撑垮整张表。信息一条没丢，可读性塌了——这正是 7.4 所指的「降级」。

**决定：优先级反转为「覆盖层 → 源」，说明与签名一体适用。** 新增 `SignatureMap`，
键同为 `${from}.${name}`，仅用于 functions 形态。

这既不增加人工负担，也不减损守卫：

- 不写覆盖时自动取源文本，FormRender 那 97% 的 TSDoc 照样白拿，人工条目仍可为零
- 函数与字段的存在性、改名、消失，仍全部由脚本按 `fields` 校验——那才是旧
  `hooks-reference.ts` 真正缺失的东西。让渡的只是文本呈现，不是校验

不选「脚本自动简化签名」：只提参数名不提类型尚可机械化，但返回类型缩写到
`{ get, post, ... }` 没有不武断的规则，那是人的判断。

**代价**：收敛信号失去原意。「该覆盖已冗余可删」的前提是上游总是更优，已被实测证伪
（6 条并存中 4 条人写版更适合橱窗）。故提示降级为中性告知，覆盖层不再随上游完善自动缩小。
接受——「缩小」的前提本就是「上游更好」，而那需要人逐条判断。

## Risks / Trade-offs

**R1：无 CI，守卫只在有人执行脚本时生效** → 缓解：`npm run gen:reference` 显式化该动作，
并在 CLAUDE.md 记入「升级 heitu 后必须重跑」及该约定当前无自动强制这一事实。
残余风险是真实的：`npm update heitu` 后无人重跑，页面会静默陈旧。橱窗场景下接受此代价。
若日后要开第一个 CI workflow，本 change 提供了一个失败条件明确、易于自动判定的起点
（重跑脚本 + `git diff --exit-code`）。

**R2：Canvas 的约 35 条覆盖需要 canvas 引擎领域知识** → 缓解：该批次不得交给不熟悉该模块的
执行者凭字段名臆测。`border: 0 | 1 | 2` 的三个取值语义必须查证 `../heitu-platform` 源码或实测确认。
猜错的说明比空白更有害——空白会被脚本拦下，错误的说明会原样上线。

**R3：覆盖层的说明质量不受 heitu 侧约束** → 缓解：脚本在两者并存时输出中性提示，使分歧可见、
供人复核。注意 D11 之后覆盖层**不再随上游完善自动缩小**（那需要人逐条判断哪一版更适合橱窗），
残余风险是人写版与上游长期分叉，橱窗场景下影响有限。

**R5：守卫全是「存在性」守卫，对「取到了错值」零覆盖** → 三条守卫查的都是「在不在」：接口在不在、
字段在不在、说明空不空。它们对「字段在、说明不空、但取到的是错的那一份」完全无感——脚本零退出、
页面不空白、无任何提示。

本 change 实施期间该缝已被踩中两次：
其一，生成脚本里 `const signatures = new Set(...)` 遮蔽了外层的 `SignatureMap`，取人写签名恒为
`undefined`，11 条人工签名一条未生效，页面照常渲染机器版长签名；
其二，D11 反转优先级之前，按逐条判断保留的 4 条人工说明实际全被上游 TSDoc 盖过，页面显示的
正是被判定为更差的那一份。

两次都是静默取错值，都不是靠守卫发现的——前者是 eslint 的 no-unused-vars 顺手抓到（它抓的是
「外层变量从未被读」这个副作用，而非「取错值」这个后果，换个写法就抓不到），后者是人肉眼比对
生成物才发现。这类失效比脚本崩溃危险得多：崩溃必然被发现，静默取错值只在有人逐条核对时才露头。

→ 缓解（8.5 已实施）：脚本追加一条**结果验证**——人写 N 条覆盖/签名，产物中必须命中 N 条，
未命中者逐条列出「人写 vs 产物实际采用」并非零退出。这是从「存在性」跨到「结果一致性」的一步。

**该检查放在主流程默认执行，而非仅 `--check` 模式**：上述两次事故都发生在日常
`npm run gen:reference` 时，若验证只在主动调用的模式下生效，两次照样会溜过去。防静默失败的
检查放在默认路径上才有意义——R1 记录的恰恰是「没人会记得」。代价是每次生成多比对 92 条，无感。

实施后以脚本副本注入缺陷做了回归验证：重现「取签名恒 undefined」与「优先级改回 doc || override」
两次事故，新检查均以非零码退出并指明分歧字段；键名拼错、产物未重跑亦各自报错。

连带：孤儿键（人写了但无清单条目使用）由提示升为错误——键名拼错与「留着备用」在文件里无法
区分，而拼错的代价是说明静默失效。

**R4：策展清单本身可能滞后于 demo** → demo 改动后新用到的字段若未加入清单，页面会缺说明而
脚本不报错（清单未点名即不校验）。这是 D4 规则的固有盲区，当前接受；如需收紧，需让脚本反向
解析 demo 源码，成本显著高于收益。

  在展示活的配置对象。字段表与它是并排两栏，还是点击字段高亮到代码对应行？后者会让该页从
  「文档」变为「可探索的东西」，更配得上作品集，但成本更高。**此问题未决，不阻塞脚本与数据层实现**
  ——建议先交付数据，展示形态单独决定。
