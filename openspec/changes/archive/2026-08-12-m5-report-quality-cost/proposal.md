# Proposal: M5 大项目报告质量 + 索引成本优化

## Why

M4 验收后的真实使用暴露两类问题。**报告质量在大项目塌方**（ad.anynovel.app，49 模块/1160 文件实测）：需求文档因 49 个 L3 摘要塞单个 prompt 超限而降级为拼接；思维导图 1739 节点 6589px 被压进页面容器完全不可读；时序图 3/6 因大模块链路数据过大降级文字——M3 报告生成按 6 模块小项目校准，规模化即失效。**索引成本偏高**：首次录入一个中型项目 L2 摘要 10-15 万 token，其中测试/类型定义/纯导出等约 30-50% 文件用 LLM 摘要纯属浪费。

## What Changes

- **思维导图分层**：报告只存模块级顶图（Project→Module，~50 节点必然可读，节点带文件数）；模块内文件子导图由前端从模块地图数据即时拼装（零后端存储、零 LLM），点击模块展开
- **新增模块数据流图**（回应"流程图"缺口）：模块间 CALLS_API 与 IMPORTS 聚合边的 Mermaid flowchart，程序化生成零幻觉，报告新增第四件
- **需求文档分批生成**：每批 ≤10 模块并发生成章节，最后单独生成系统概述；单批失败仅该批章节降级拼接，不再整篇塌方
- **时序图输入瘦身**：链路数据仅取模块入口文件 L2 + 入口相关边（各类上限条数），大模块截断并标注
- **规则分级摘要**：测试文件、类型定义/.d.ts、纯导出 barrel、配置常量、<30 行小文件走确定性规则摘要（免 LLM），仅业务逻辑文件走 LLM 精读——预计砍掉 40-60% 摘要调用
- **L2 输入按文件体量分级**：小文件不再塞满额头部与符号清单
- **索引深度双模式**：录入/重索引支持 `depth=deep|fast`（默认 deep）。fast 跳过全部 LLM 摘要与报告（规则摘要占位 + 路由地图 + 图结构 + 代码检索全保留，近零 LLM 成本）；详情页提供「生成深度理解」按钮补跑 summarize+report

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `understanding-report`: 「报告三件套生成」→ 四件（分层导图 + 数据流图 + 分批文档 + 瘦身时序图）；「报告生成降级与校验」降级粒度细化到章节/批；「前端项目理解展示」增加模块子导图展开与数据流图
- `indexing-pipeline`: 「四层摘要生成」增加规则分级与输入分级；新增「索引深度模式」需求
- `project-management`: 「触发索引任务」增加 depth 参数；「项目详情页」增加「生成深度理解」入口

## Impact

- 代码：`services/report/`（分批/分层/数据流图）、`services/ingest/summarizer.py`（规则分级）、pipeline（depth 分支）、前端详情页（子导图展开、数据流图、深度按钮）
- 成本：中型项目首次录入摘要成本预计降至 1/3；fast 模式近零
- 兼容：已有报告结构增加 dataflow_mermaid 字段（可空），旧报告前端兼容展示；无迁移（understanding_reports 新列一条 alembic）
