# M11: 用户管理（admin 查看用户 + 禁用登录）

## Why

M8 给了邀请码准入，但管理员看不到"谁进来了"，也无法收回权限——邀请码发出去就管不住了。
用户确认三点：**禁用而非删除**（可恢复、不丢数据）、列表要看到完整画像、**项目不动**
（项目本就全局共享，与人无关）。

## What Changes

| # | 变更 | 说明 |
|---|------|------|
| 1 | users 加 `disabled_at` / `last_login_at`（alembic 0008） | 均可空；登录成功写 last_login_at |
| 2 | `GET /auth/users`（admin） | 用户名、角色、注册时间、最后登录、**所用邀请码**（invite_codes 反查）、会话数、提问数 |
| 3 | `POST /auth/users/{id}/disable` / `/enable`（admin） | 禁用即刻失效，不等 JWT 过期 |
| 4 | 守卫校验禁用态 | **关键**：JWT 无状态，禁用后旧 token 默认还能用满 7 天 |
| 5 | 前端 `/users` 管理页（admin） | 列表 + 禁用/恢复，被禁用行灰显 |

## 关键技术决策

**禁用如何即刻生效**：`require_user` 依赖在解析 JWT 后**查一次库**确认 `disabled_at IS NULL`。
代价是每个业务请求多一次主键查询（个人自用规模无压力），换来"点击禁用立即生效"的确定性。
备选方案 token_version（JWT 内嵌版本号）省这次查询，但要改签发与校验两侧、且注销早于过期
的语义要另做——当前规模不值得。

**安全护栏**（少一条就能把自己锁在系统外）：
- 不能禁用自己
- 不能禁用最后一个启用状态的 admin
- 被禁用用户的 MCP 接入不受影响（MCP 走独立 token，与账号体系解耦，M7/M8 已确立）

## 不做什么

- 不做删除用户（用户已选禁用；真要删可后续加，需先定会话与邀请码的级联语义）
- 不做改密码/重置密码（v1 克制，与 M8 一致）
- 不做角色调整（member ↔ admin 互转）

## Capabilities

- `auth`（MODIFIED）：用户列表、禁用/恢复、守卫校验禁用态
